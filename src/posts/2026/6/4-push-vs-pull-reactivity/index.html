In the docs for RxJS there is a tidy table that lays out the distinction between push and pull over single and multiple values as arguments:

SINGLE MULTIPLE
Pull Function Iterator
Push Promise Observable

What tidiness! What pure, Platonic satisfaction it gives! Of course, this table is nice, but only as far as it markets why RxJS exists: push strategies need a primitive. (And, I wonder, is this a fundamental leaning that all languages succumb to?)

You can actually adjust this table to include more examples, which might help illustrate these four quadrants better:

SINGLE MULTIPLE
Pull
  • Function
  • Getter (get foo())
  • Plain property / variable read
  • Thunk/callback (() => value)
  • Iterator / generator (function*)
  • Any iterable (Symbol.iterator)
  • Cursor / next() / paginated fetch
Push
  • Promise
  • Callback (before promises, like (err, value) => {})
  • requestAnimationFrame / setTimeout
  • once: true event listener
  • Events (addEventListener)
  • Observable

After thrashing about in the reactive framework landscape for the last few months I've noticed a few themes:

  • Programming languages generally don't start with "push" in their design - In the table you can see that the push row developed later in Javascript's life- promises were included in the Ecmascript standard after A+ was formulated, and observables have no comparable primitive in the standard today.
  • Frameworks gravitate towards "pull" actions by the nature of the problems they solve - This leaning is a result of frameworks dealing with consistency, idempotency, and efficiency forces.
  • There really isn't a pure push framework. - The closest I can find is Svelte 4, but even that could be considered slightly pull.

Let's go further.

It's really difficult to pin down what would make a "push" framework

The main reason this is really difficult is that all frameworks or reactivity systems need to "nudge" the system in some way. In React, using a setState() hook will schedule re-renders generally. In Ember, setting a tracked property will nudge a clock. In wc-services, notify() is called. With signals, tracked depenencies are directly informed.

If invalidation were technically a "push", all frameworks would be considered push-pull and the push-to-pull axis that I've been talking about collapses and is meaningless. There is something more than just nudging the framework with an invalidation. It has to do with dependencies and how the system solves the diamond problem.
